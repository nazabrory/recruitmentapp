# Research: In-browser selfie video recording on mobile browsers

Ticket: #4 · Date: 2026-11-04 · Scope: can a candidate record a ~60s selfie intro video directly in a mobile browser, reliably enough to build on, for Indonesian SMEs (many low-end Androids, some iPhones, flaky connections)?

**Verdict: Yes — buildable, with a feature-detected MediaRecorder path plus a file-upload fallback, a hard size cap, and resumable uploads. For a first demo, ship upload-only; recording is a strict superset that can be added later behind the same upload endpoint.**

---

## 1. Support matrix: getUserMedia + MediaRecorder

`getUserMedia()` is the gate: it prompts for camera/mic and yields a `MediaStream`. `MediaRecorder` consumes that stream and produces compressed chunks. Both are required for in-browser recording; either missing ⇒ fall back to file upload.

| Browser | getUserMedia | MediaRecorder | Notes |
|---|---|---|---|
| Chrome Android | Yes (since ~Chrome 47 mobile era; secure-context only) | Yes | MDN marks getUserMedia "Baseline — Widely available"; MediaRecorder "Baseline — Widely available": [MDN MediaRecorder](https://developer.mozilla.org/en-US/docs/Web/API/MediaRecorder), [MDN getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia) |
| iOS Safari | Yes since iOS 14.0 (Sep 2020) | Yes since iOS 14.3 (MP4/H.264+AAC); WebM recording only since iOS 18.4 | caniuse: MediaRecorder supported Safari iOS 14+ ([caniuse mdn-api_mediarecorder](https://caniuse.com/mdn-api_mediarecorder)); WebKit shipped MediaRecorder in iOS 14.3 ([WebKit blog 11353](https://webkit.org/blog/11353/mediarecorder-api/)) |
| iOS 13 and earlier | No (Safari-only legacy API, unreliable) | No | caniuse shows Safari iOS 3.2–13.7 unsupported ([link](https://caniuse.com/mdn-api_mediarecorder)) ⇒ these devices must use the upload fallback |
| Other iOS browsers (Chrome/Firefox on iOS) | Only since iOS 14.3, via WKWebView exposure | Same as Safari (WebKit) | Apple enabled getUserMedia in WKWebView in iOS 14.3 ([WebKit blog 11353](https://webkit.org/blog/11353/mediarecorder-api/); long-running gap documented in [WebKit bug 208667](https://bugs.webkit.org/show_bug.cgi?id=208667)). All iOS browsers are WebKit ⇒ Safari version is the only thing that matters |
| Samsung Internet | Yes | Yes (since v5) | Chromium-based; caniuse lists Samsung Internet 5–30 supported ([link](https://caniuse.com/mdn-api_mediarecorder)). Behaves like Chrome Android (WebM default) |

Codec support by engine:

- **Chromium (Chrome Android, Samsung Internet, Edge Android):** default output WebM (VP8/VP9 + Opus) (`video/webm`); MP4/H.264+AAC recording added in **Chrome 126** ([chromestatus feature 5163469011943424](https://chromestatus.com/feature/5163469011943424), [Chrome 126 release notes](https://developer.chrome.com/release-notes/126#media); history in [crbug 40127044](https://issues.chromium.org/issues/40127044)). Feature-detect with `MediaRecorder.isTypeSupported()` ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/MediaRecorder/isTypeSupported_static)).
- **WebKit (all iOS browsers):** MP4 + H.264 + AAC from the start ([WebKit blog 11353](https://webkit.org/blog/11353/mediarecorder-api/)); Safari 18.4 (iOS 18.4) added WebM/Opus/VP8/VP9, fragmented MP4, and more codecs ([WebKit "Safari 18.4 features", Media section](https://webkit.org/blog/16574/webkit-features-in-safari-18-4/)).
- Low-end Android gap: even where APIs exist, software VP8 encoding on weak SoCs can drop frames or overheat; older WebView-based browsers (in-app WebViews in WhatsApp/LINE/Instagram, stock "Android Browser" pre-Chromium) lack the APIs — caniuse lists Android Browser 2.1–4.4.4 unsupported ([link](https://caniuse.com/mdn-api_mediarecorder)). Treat "opened inside a social-app webview" as a realistic failure mode and route to the fallback.

## 2. iOS-specific quirks (the critical ones)

1. **HTTPS is mandatory — hosting implication.** `getUserMedia()` exists only in secure contexts; over plain HTTP `navigator.mediaDevices` is `undefined` (calling it yields `TypeError`/`NotAllowedError`) ([MDN getUserMedia — Privacy and security](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)). Exceptions: `localhost` and `file:///`. So the app **must be served over HTTPS** (a free Let's Encrypt cert or a CDN like Cloudflare/Vercel with automatic TLS is sufficient; this is not a cost barrier).
2. **Permissions UX.** Safari shows one per-origin prompt per device type: asking for `{audio, video}` produces *two* consecutive prompts (camera, then microphone) ([WebKit bug 208667 comment 66/70](https://bugs.webkit.org/show_bug.cgi?id=208667)). If the user denies once, the page cannot re-prompt — they must flip the setting in Safari site settings ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia): "user has denied access for the current session… globally"). UI must explain *why* before prompting, and detect `NotAllowedError` to show "enable camera in Settings → Safari" guidance.
3. **Page must be visible/focused.** WebKit gates the permission prompt on document visibility (`getUserMediaRequiresFocus` setting; request is deferred until the document becomes visible) ([WebKit source: MediaDevices.cpp](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/Modules/mediastream/MediaDevices.cpp)). Don't call `getUserMedia` on page load in a background tab; call it from an explicit user tap on the visible recorder screen.
4. **Output codec/container — the webm problem.** Safari 14.3–17.x records **MP4 only** and will reject a `video/webm` request (`isTypeSupported('video/webm')` was false until 18.4) ([WebKit 11353](https://webkit.org/blog/11353/mediarecorder-api/), [WebKit 18.4](https://webkit.org/blog/16574/webkit-features-in-safari-18-4/)). Conversely Chrome records WebM by default, and **iOS Safari cannot play WebM** historically — MDN's WebM row shows Safari support only in recent versions ([MDN containers guide](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats/Containers)). Consequence: **store MP4 (H.264/AAC) whenever the browser can produce it** — it is the single container that plays everywhere (MDN: "If for any reason you are only able to provide media in a single format, choose … MP4" — [link](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats/Containers)). For WebM from Android, either transmux server-side or also accept it (see §3).
5. **Metadata bug class on iOS.** Early Safari (14.0) shipped a MediaRecorder regression producing MP4s with broken duration metadata — unplayable outside Safari until fixed in 14.1 ([WebKit bug 216832](https://bugs.webkit.org/show_bug.cgi?id=216832)). Even current Chrome/Safari emit **fragmented MP4 whose `moov` atom carries duration = 0**, so players must download the whole file before seeking and some players (e.g. Windows Media Player) misbehave ([AddPipe: Duration in MP4 files produced by Chrome/Safari](https://blog.addpipe.com/duration-in-mp4-files-produced-by-chrome-safari/)). ⇒ **Plan a server-side normalization pass** (`ffmpeg -movflags +faststart`, or remux with mp4box.js) after upload; don't trust the browser's bytes as the final artifact.
6. Real-device reports (Apple Developer Forums) note front-camera recording quirks persisting into iOS 18 ([thread](https://developer.apple.com/forums/forums/topics/safari-and-web-topic/safari-and-web-topic-general?page=2)) — another reason to keep a retake flow and an upload fallback.

## 3. Compression and upload for flaky networks

**File size math for 60 s** (bytes ≈ bitrate_bps ÷ 8 × seconds):

| Setting | Video | Audio | 60 s size |
|---|---|---|---|
| 720p30 @ 1 Mbps + 64 kbps AAC | ~7.5 MB | ~0.5 MB | **~8 MB** |
| 720p30 @ 2 Mbps + 96 kbps | ~15 MB | ~0.7 MB | **~16 MB** |
| 1080p30 @ 4 Mbps + 128 kbps | ~30 MB | ~1 MB | **~31 MB** |
| VGA (640×480) 24–30fps @ 700 kbps | ~5.3 MB | ~0.5 MB | **~6 MB** |

`MediaRecorder` accepts `videoBitsPerSecond` / `audioBitsPerSecond` / `mimeType` options ([MDN MediaRecorder constructor](https://developer.mozilla.org/en-US/docs/Web/API/MediaRecorder/MediaRecorder)); `avc1.424028,mp4a.40.2` (H.264 CBP L4 + AAC-LC) is the "good for mobile and resource-constrained" profile per MDN's [mimeType page example](https://developer.mozilla.org/en-US/docs/Web/API/MediaRecorder/mimeType). Camera capture prefers resolutions via `ideal` constraints, which never hard-fail ([MDN getUserMedia constraints](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)).

**Browser-side re-encoding (compression after recording):** WebCodecs `VideoEncoder` + mp4-muxer is the modern route, but hardware H.264 encode support on Android WebView/Safari is uneven, and software re-encode of 60s video is CPU/heat-heavy on low-end phones. **Do not** build re-encoding into v1; choose a conservative capture bitrate up front, and do any quality normalization **server-side with ffmpeg** (faststart + duration metadata), as AddPipe also recommends ([link](https://blog.addpipe.com/duration-in-mp4-files-produced-by-chrome-safari/)).

**Resumable/chunked upload (essential for flaky connections):**

- **tus 1.0.0** (open HTTP protocol): `POST` creates the upload (`Upload-Length`), `PATCH` sends `application/offset+octet-stream` chunks at the server-reported `Upload-Offset`; a dropped upload resumes with only the remaining bytes; `HEAD` reveals the offset; extensions add creation-with-upload, checksums (per-chunk SHA-1), expiration, termination ([tus protocol spec](https://tus.io/protocols/resumable-upload)). `tus-js-client` runs in browsers (and React Native/Cordova) with `retryDelays` and `findPreviousUploads()` resume-after-reload ([tus-js-client README](https://github.com/tus/tus-js-client)). This is the best fit: it works with a Blob made of MediaRecorder chunks *or* a picked file, so one code path serves recording and fallback upload. Chunk the Blob with `File.slice()` and small PATCH sizes (e.g. 256–512 KB) so each retry is cheap on 3G.
- **S3-style multipart** (if storing on S3/R2): CreateMultipartUpload → UploadPart (parts ≥5 MB min except last, ≤15 MB part size recommended, max 10,000 parts) → Complete; failed parts retried individually, "quick recovery from any network issues" is AWS's stated benefit ([AWS S3 multipart overview](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html), [CreateMultipartUpload API](https://docs.aws.amazon.com/AmazonS3/latest/API/API_CreateMultipartUpload.html)). Pair with presigned URLs per part. For an ~8–20 MB file this is fine but tus is simpler to make resumable across page reloads; S3 multipart state lives in the upload ID you must persist client-side anyway.
- Set **expiry/lifecycle cleanup** for abandoned uploads (tus `expiration` extension; S3 `AbortIncompleteMultipartUpload` lifecycle rule) so flaky sessions don't leak storage ([both docs above](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html)).

## 4. Fallback ladder when in-browser recording fails

1. **In-browser record** (getUserMedia + MediaRecorder, MP4-preferred via `isTypeSupported` probing).
2. **Native camera capture via `<input type="file" accept="video/*" capture="user">`** — HTML Media Capture: OS presents its own camera UI (front camera requested via `capture="user"`), which works even in browsers/webviews lacking getUserMedia/MediaRecorder, and even over plain HTTP ([MDN capture attribute](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Attributes/capture), [HTML Media Capture spec](https://w3c.github.io/html-media-capture/#dfn-capture)). Output is a native MP4/MOV file (moov-at-end; same faststart normalization applies — [AddPipe](https://blog.addpipe.com/duration-in-mp4-files-produced-by-chrome-safari/)). Caveat: OS camera UI can't enforce a hard 60 s limit — reject over-long/oversized files client-side and ask for a retake.
3. **Plain file upload** (`accept="video/*"`, no capture) — candidate records with their phone's camera app and uploads the file. Same resumable-upload endpoint.
4. **Post-apply link / async path** — email/WhatsApp the candidate a unique HTTPS link to complete the video step later from a better device or connection; the application is accepted pending video. Cheap to implement (token URL + same flow) and the only humane option when the device itself lacks a working camera path.

Ladder logic is feature-detection driven: `!!navigator.mediaDevices?.getUserMedia && 'MediaRecorder' in window && MediaRecorder.isTypeSupported(chosenType)` → tier 1, else tier 2/3. Never dead-end a candidate.

## 5. Capture UX constraints (preview + recording screen)

- **Front camera:** `video: { facingMode: "user" }` prefers the selfie camera ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)); use `ideal`, not `exact`, since not every device reports a user-facing camera (reject with `OverconstrainedError` otherwise). Note Safari historically ignored many constraints — treat resolution/facing as best-effort and verify on real devices.
- **Inline preview:** `<video>` with `srcObject = stream`, `playsinline` + `muted` autoplay for the live preview ([WebKit MediaRecorder example uses autoplay playsInline muted](https://webkit.org/blog/11353/mediarecorder-api/)).
- **Countdown then auto-start** (3-2-1), **on-screen timer**, and **auto-stop at max length**: MediaRecorder has no built-in duration limit — enforce with `setTimeout(() => recorder.stop(), 60_000)` plus a soft warning at e.g. 50 s. `start(timeslice)` gives periodic `dataavailable` blobs ([MDN MediaRecorder.start](https://developer.mozilla.org/en-US/docs/Web/API/MediaRecorder)), so you can cap by cumulative bytes as well as time: stop early if `bytes/second` implies > cap at 60 s.
- **Retake:** keep the recorded Blob + object-URL preview, "Use video" / "Retake" buttons; always release tracks on retake/leave (`stream.getTracks().forEach(t => t.stop())`) or the camera indicator stays on and low-end devices leak ([WebKit example — endRecording stops tracks](https://webkit.org/blog/11353/mediarecorder-api/)).
- Stop recording **before** upload completes UI leaves the page; if the app must survive a mid-upload navigation, tus's `findPreviousUploads()` can resume ([tus-js-client](https://github.com/tus/tus-js-client)).
- Keep the whole step **optional-to-skip in UI copy** ("rekam video, atau unggah file dari galeri") — supports the fallback ladder without user dead-ends.

## 6. Testing tooling for real-device browsers

- **Android (Chrome/Samsung Internet):** USB remote debugging via `chrome://inspect#devices` — full DevTools + screencast against the device's actual Chrome ([Chrome DevTools remote debugging](https://developer.chrome.com/docs/devtools/remote-debugging)); `adb forward tcp:9222 localabstract:chrome_devtools_remote` for scripting against the device CDP.
- **iOS Safari:** Web Inspector over USB from macOS — enable Settings → Safari → Advanced on the iPhone, then the Develop menu on the Mac ([Apple: Inspecting iOS and iPadOS](https://developer.apple.com/documentation/safari-developer-tools/inspecting-ios)); Responsive Design Mode + "Open with Simulator" for quick iOS-version sweeps ([WebKit Safari 18.4 post](https://webkit.org/blog/16574/webkit-features-in-safari-18-4/)).
- **Cloud real-device labs:** BrowserStack Live/App Live on real iPhones/Samsung/Galaxy devices, with **camera video injection** and **microphone audio injection** so getUserMedia/`<input capture>` flows can be exercised without a human holding a phone ([BrowserStack real device features](https://www.browserstack.com/real-device-features), [media injection](https://www.browserstack.com/real-device-features/media-injection-and-audio-streaming)). Same capability exists on Sauce Labs/AWS Device Farm; LambdaTest offers camera injection for web. Note: camera injection ≠ true front-camera realism — regression-test the golden path on ≥1 owned cheap Android.
- **Tunnel for device testing against localhost:** any ephemeral HTTPS tunnel works — Cloudflare Quick Tunnels give a temporary `trycloudflare.com` HTTPS URL with no account ([Cloudflare docs](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/)); this satisfies the secure-context requirement (§2.1) while testing from real phones.
- **CI:** Playwright/webdriverio can drive Chrome Android via adb/CDP for the upload fallback; in-browser camera recording in headless CI should be mocked (e.g. fake device flags) — do end-to-end verification on devices, not CI.

## 7. Recommendation (build-on-this defaults)

- **Capture settings:** `getUserMedia({ audio: true, video: { facingMode: "user", width: { ideal: 1280 }, height: { ideal: 720 }, frameRate: { ideal: 30 } } })`; recorder options: try, in order, `video/mp4; codecs="avc1.64001F,mp4a.40.2"` → `video/mp4` → `video/webm; codecs="vp8,opus"` via `MediaRecorder.isTypeSupported()`; **`videoBitsPerSecond: 1_000_000`, `audioBitsPerSecond: 64_000`**, `start(1000)` for 1 s timeslice chunks.
- **Container to store:** **MP4 (H.264/AAC)** — the only universally playable format on iOS, Android, and desktop players ([MDN containers](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats/Containers)). On WebM-only browsers, upload WebM and transcode/remux server-side to H.264 MP4 (ffmpeg) — one async worker job.
- **Post-upload normalization always:** faststart (`-movflags +faststart`) + duration metadata repair, because browser-emitted MP4s are fragmented with duration=0 ([AddPipe](https://blog.addpipe.com/duration-in-mp4-files-produced-by-chrome-safari/), [WebKit 216832 history](https://bugs.webkit.org/show_bug.cgi?id=216832)).
- **Hard caps:** duration ≤ 60 s (enforced in UI by timer + auto-stop); file size ≤ **20 MB** (reject/retake above it; the 720p/1 Mbps target lands ~8 MB with margin). Server-side: reject > 25 MB regardless of path.
- **Hosting:** HTTPS is mandatory for recording — deploy behind any TLS-terminating CDN/host with auto-renewed certs.
- **Upload:** tus 1.0.0 (tus-js-client) with `retryDelays`, 256–512 KB PATCH chunks, resume-on-reload; server-side expiry for abandoned uploads. (S3 multipart + presigned parts is an acceptable equivalent if you'd rather not run a tusd/tus server.)
- **Fallback ladder:** record → `<input capture="user">` → file upload → post-apply link (§4). Surface the fallbacks on the same screen, don't wait for an error.

## 8. What to stub in the demo

**Yes — start upload-only.** Ship the video step as: `<input type="file" accept="video/*">` (with `capture="user"` on mobile) + size/duration validation + resumable upload + preview player. This exercises 100% of the server contract (storage layout, MIME handling, normalization job, HR playback view) with ~20% of the frontend complexity, and is already usable by candidates on old iPhones (< iOS 14) and in-app webviews. Add the MediaRecorder screen in a later iteration behind feature detection; nothing in the upload/storage/normalization path changes. Stub: fake camera (pre-recorded clip picker) for demos on a laptop is fine — just don't demo getUserMedia live unless you've tested that exact machine.
